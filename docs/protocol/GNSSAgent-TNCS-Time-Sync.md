# GNSSAgent-CCU 向 TNCS 授时

仅 `buildinfo.Target=ccu` 的构建启用，连接本机 `127.0.0.1:44622`。
其他目标不创建 TNCS 客户端。此功能不修改操作系统时钟。

## 发送规则

- 校验通过、可识别的 NMEA 报文进入解析回调时刷新断流计时。
- RMC/ZDA 中日期与 UTC 时间字段完整且合法时可以授时，不检查导航有效状态、GST RMS 或时间质量收敛结果。
- TCP 可用时，首次完整 UTC 立即交给独立发送流程，发送 `trusted=true`。
- 请求写完后等待 30 秒，再发送下一条新到达的完整 UTC；等待期间不保存待补发的时间。
- TCP 连接/响应等待期间不阻塞 GNSS 接收，不积压授时报文。重新连接后只使用新到达的完整 UTC，并保留上一请求的 30 秒发送间隔。
- 时间戳为 UTC Unix 毫秒，不加时区偏移。软件不对 NMEA 输出和传输延迟进行估计补偿；接口传输毫秒时间不代表绝对毫秒级授时精度。

## 断流与恢复

- 连续 30 分钟没有可识别且校验通过的 GNSS 报文，发送 `timestamp_ms=0, trusted=false`。启动后一直无数据也适用。
- 断流检测每秒执行一次，使用本地单调时钟；完整 UTC 不用于断流计时或失效上报。
- 失效上报成功后不重复发送；拒绝或传输失败则重试，重试间隔至少 3 秒。
- 接收恢复后，新的完整 UTC 恢复可信授时。仅收到不含完整 UTC 的报文会刷新断流计时，但不会凭空恢复可信授时。
- 连接恢复后，如仍处于断流状态，会重新上报失效，以覆盖 TNCS 重启场景。

## 连接与异常

- 启动立即尝试连接，失败后每隔 3 秒重试，不限制次数，直到成功或程序退出。
- TNCS 尚未启动时持续等待重连；GNSS 接收、聚合和订阅发布继续工作。TNCS 就绪后自动连接，无需重启 GNSSAgent。
- 曾经连接成功后的传输异常，每隔 3 秒尝试重连，直到成功或程序退出。
- 单次连接与请求 I/O 超时均为 3 秒，退出信号可中断等待。
- TNCS 业务拒绝会记录原因，不计为成功；可信授时下一次仍采用新报文，失效通知则重试。

## 协议与 TNCS 依赖

TCP 长连接，无需 ServiceLogin。帧为 4 字节大端长度（不含自身）加 Protobuf `TncsMsg`。
请求消息类型 `101008`，响应消息类型 `201008`，协议子集见 `internal/tncstime/set_local_time.proto`。
响应必须为对应类型且 `success=true`，否则记录失败。客户端支持 TCP 分片、部分写入并限制响应帧大小。

失效语义是双方新增约定：`timestamp_ms=0, trusted=false` **仅清除可信状态，不把 TNCS 时间设为 0**。
Proto3 的 0/false 可省略编码，因此此请求的业务 payload 可为空。TNCS 必须接受默认字段并清除查询及邻居授时所使用的可信状态。
旧版 TNCS 会拒绝该请求并返回 `invalid timestamp_ms`，需要升级 TNCS 后才能完成失效联调。

## 验证

`go test ./...` 覆盖发送间隔、新鲜 UTC、断流、恢复、启动重试、断线重连、业务拒绝、协议分片和退出。
设备联调需使用已实现上述失效语义的 TNCS，核对可信时间写入以及 0/false 后的时间连续性和可信度变化。
